# Production Server Info — `malaria.health.go.ug`

> Living record of the live Martbase (dhis2-superset) production server, so any
> deploy or debugging starts from the real state. Last verified: **2026-07-21**.

## Domain

- **Current domain: `malaria.health.go.ug`**
- Old/retired domain: `supersets.vitalplatforms.com` — **do NOT let any script
  revert to this.** It is hardcoded as a default in the `superset-manager-v2*.sh`
  scripts (`SUPERSET_BASE_URL` default + nginx `server_name` from `DOMAIN`), so
  those scripts must never be run wholesale without `DOMAIN=malaria.health.go.ug`.

## Inside the `superset` container

- **App / git checkout:** `/opt/dhis2-superset`
  - Remote: `https://github.com/HISP-Uganda/dhis2-superset.git`
  - Branch: `martbasev1`
  - Code runs **directly from this checkout** via `PYTHONPATH=/opt/dhis2-superset`
    (NOT pip-installed) → a git update + service restart is enough for backend.
- **Venv:** `/opt/superset-venv`
- **Runtime config (holds `SECRET_KEY`):** `/opt/dhis2-superset/superset_config.py`
  — pointed to by `SUPERSET_CONFIG_PATH`. **Never overwrite** (would break the
  domain and make existing encrypted secrets undecryptable).
- **Env file:** `/etc/superset/superset.env` (outside the checkout) — sets
  `SUPERSET_CONFIG_PATH`, `PYTHONPATH`, `SQLALCHEMY_DATABASE_URI`, `DATABASE_URL`.
  Header notes it was managed by the server-only
  `sync-vitalplatform-config-safe-dbpass-and-fix-superset-public.sh` (not in repo).
- **Toolchain:** Node 20.20, npm 10.8, ~62 GB RAM (on-server frontend build fine).
- **Built assets:** `superset/static/assets/` (webpack output, served directly).

## systemd services (all run as user `superset`, WorkingDirectory `/opt/dhis2-superset`)

- **`superset.service`** — gunicorn web. Sources `/etc/superset/superset.env`, then:
  `gunicorn --workers 4 --worker-class sync --timeout 300 --bind 0.0.0.0:8088 "superset.app:create_app()"`
- **`superset-worker.service`** — celery worker. `celery --app=superset.tasks.celery_app:app worker --pool=prefork -O fair --concurrency=4 --queues=celery,dhis2`; pid/log under `/opt/dhis2-superset/run/` + `/logs/`.
- **`superset-beat.service`** — celery beat. Schedule + pid under `/opt/dhis2-superset/run/`.
- Restart all: `systemctl restart superset superset-worker superset-beat`

## Database / migration state (verified 2026-07-21)

- Metadata DB is **PostgreSQL** (postgres container), not SQLite.
  - ⚠️ Running `superset` from a plain shell **without** sourcing
    `/etc/superset/superset.env` falls back to an empty local **SQLite** with a
    default secret key. Always `set -a; . /etc/superset/superset.env; set +a`
    first, or you'll read the wrong (empty) DB.
- **Alembic revision: already at head `2026_04_03_fix_ai_insights_encrypted_secrets_type`.**
  → `superset db upgrade` is currently a **no-op**; no schema change pending.
- **Roles present:** `Admin, Alpha, Analytic, Data Management, End User, Gamma,
  Public, sql_lab`.
  - ⚠️ Naming mismatch vs code: code defines `Analytics` / `End user`; prod has
    `Analytic` / `End User` (created manually — `dbc2bae` had no role-spec code).
    Reconcile with a name rename before `superset init` (see deploy script).

## Files that must NEVER be overwritten / regenerated by a deploy

- `/opt/dhis2-superset/superset_config.py` (`SECRET_KEY`, DB URI, domain-linked)
- `/etc/superset/superset.env`
- ClickHouse credentials (`/etc/clickhouse-server/clickhouse.env`)
- The `proxy` container's nginx config (domain / TLS)

## Backups (operator convention — manual)

- App dir snapshots: `dhis2-superset.backup_before_fresh_clone_<ts>` (snapshot-
  then-refresh is the established pattern).
- ClickHouse: `clickhouse-access-backup-<ts>`, `clickhouse-schema-before-*`.
- Metadata: `pg_dump -Fc` from the postgres container.

## Deploy mechanism

- Use the purpose-built **`deploy-malaria-update.sh`** (in repo root): backup →
  role-name reconcile → git fast-forward → restore protected config → build →
  `db upgrade` (no-op) → `init` → restart. It does **not** regenerate config,
  env, nginx, or the domain.
- Do **not** run `superset-manager-v2*.sh` / `deploy-supersets*.sh` wholesale —
  they regenerate config + nginx with the old `vitalplatforms.com` domain and
  can clobber `SECRET_KEY`.
