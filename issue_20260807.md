## 1. Problem statement

Newly created DHIS2 datasets (e.g. `mal_pregnancy`, `mal_prevention`) do not
survive: they **disappear from the Datasets list**, and/or their map shows
**"Empty query?"**, the **data filter is empty**, and editing throws
**"Failed to load dataset configuration for editing."** Healthy long-standing
datasets (the `MAL - …` originals) are unaffected. The failures cluster on
**recreated / re-registered** datasets.

### Symptoms seen (all trace to a small set of root causes)
| Symptom | Root cause # |
|---|---|
| Dataset vanishes from list after restart / re-create | 1, 2 |
| Map: **"Empty query?"** | 1 (→ no columns) |
| Data filter: no values | 1, 8 |
| Edit: **"Failed to load dataset configuration for editing"** | 1 (staged dataset gone) |
| Wrapper query → **404** | 3 |
| Indicator map shows summed % (e.g. 2,877%) | 4, 5 |
| Period slider dead "at times" | 6 |
| Sync returns 0 rows (indicators) | 7 |
| Sync returns ~481K rows / wrong level | 4 |

## 2. Root causes & what's been done

Legend for **Status**: ✅ committed + deployed · 🟡 committed, **NOT deployed** · ⚪ not started / config-only.

### #1 — cleanup cascade orphans the staged dataset  ← **primary root cause**
A DHIS2 staged dataset has **three** linked SqlaTables (SOURCE, MART, and the
user-facing METADATA wrapper). On SqlaTable `after_delete` the code ran
`DELETE FROM dhis2_staged_datasets` with **no check that the other tables still
referenced it**. Re-registering a wrapper deletes+recreates it → that delete
nuked the whole staged dataset → SOURCE/MART + the new wrapper are **orphaned**
(no columns, no staged config).

**Two `after_delete` handlers do this cleanup — BOTH had to be guarded:**
- `SqlaTable.cleanup_linked_dhis2_staged_dataset` (`connectors/sqla/models.py`).
- `_after_sqla_table_delete` (`dhis2/listeners.py`) — a **separate** listener
  registered via `setup_listeners`, only skipping MARTs.

Guarding just the first was **not enough** — the second listener overrode it and
still deleted the staged dataset (proven live; see the BREAKTHROUGH log entry).
- **Fix:** the same "is this the last linked table?" guard applied to **both**
  handlers. +tests in `models_test.py` and `test_cascading_delete.py` (4/4 pass).
- **Status:** models.py guard ✅ deployed (`a60f614853`, `grep remaining_links`
  = 3 on server). listeners.py guard 🟡 committed locally, **DEPLOY NEXT** —
  this is the one that actually stops the disappearing.

### #2 — startup compat backfill churns / deletes wrappers
`run_compatibility_backfill()` ran on **every** app init and re-registered /
de-duplicated DHIS2 wrappers; with duplicate datasets present its cascade
deleted live ones. Restart = dataset roulette.
- **Fix:** `DHIS2_DISABLE_STARTUP_BACKFILL` flag guards it in
  `superset/initialization/__init__.py`.
- **Status:** ✅ deployed (commit `67c2249a0c`) + flag set in `/etc/superset/superset.env`.
  Log shows `DHIS2 compat backfill skipped`.

### #3 — wrapper SQL built unquoted → routed to the DHIS2 API → 404
Wrapper SQL was `f"SELECT * FROM {serving_table_ref}"` (raw interpolation).
Unquoted `dhis2_serving.sv_N` → the DHIS2 dialect parses `dhis2_serving` as an
API endpoint → `https://hmis.health.go.ug/api/dhis2_serving` → 404.
- **Fix:** `_build_metadata_wrapper_sql()` always backtick-quotes via
  `_parse_table_ref`. +tests. Plus a one-time `repair_wrapper_sql.py` for
  existing rows.
- **Status:** ✅ deployed (commit `781445181b`). Repair script available.

### #4 — `org_unit_scope="all_levels"` (volume + indicator correctness)
Recovery/repair paths hard-code `all_levels` + a root org unit → the resolver
enumerates the whole hierarchy (levels 1–7) → ~481K rows, and for **indicators**
the map SUMs facility percentages into districts (2,877%). Scoping too high
also drops the district level entirely.
- **Mitigation:** cap `max_orgunit_level=3` / use district-level `selected`
  scope when creating.
- **Status:** ⚪ config-level only. Code change (don't force `all_levels`,
  level-aware maps) not done — larger/riskier.

### #5 — indicators re-aggregated (SUM) instead of NONE
The non-re-aggregate guard checked only `dhis2_is_indicator`; when that marker
drifted, indicators fell through to `SUM` → summed percentages.
- **Fix:** resilient detection — also honour `dhis2_variable_type` in
  `dataset_columns_payload` (`analytical_serving.py`). +tests.
- **Status:** ✅ deployed (commit `fc5d73bd0f`).

### #6 — period slider grabs the wrong / blank column
The map resolved the period column from loaded data-row keys + a name heuristic
that matched `period_variant` (often blank) → slider dead "at times."
- **Fix:** marker-driven `resolveDhis2PeriodColumn` (prefers
  `dhis2_period_key='period'`). +tests.
- **Status:** ✅ deployed (commit `7fbc43d6b5`).

### #7 — indicator analytics time out (0 rows)
50-OU chunks for indicators (heavy per-cell formula + OU count map) exceed the
Cloudflare ~100 s gateway timeout → 5xx → whole sync aborts → 0 rows.
- **Fix:** indicator-aware OU chunking (indicators at 10 OUs, data elements at
  50) + 525 added to retryable codes (`sync_service.py`). +tests.
- **Status:** ✅ deployed (commit `6ff1022e05`).

### #8 — orphan wrapper has no columns (defense-in-depth)
When the staged dataset is gone, column sync has no manifest → wrapper has no
columns → "Empty query" + empty filter. #1 prevents the orphaning; this would
make even an existing orphan self-heal.
- **Fix (proposed):** column sync falls back to introspecting the physical
  serving table when the staged dataset is absent.
- **Status:** ⚪ not started.

### #9 — data filter needs a staged link
`DHIS2ColumnFilterControl` fetches column values from the staged-dataset
endpoint; static/orphan datasets have no staged link → empty filter.
- **Fix (built earlier):** `/dhis2/staged-datasets/dataset-column-values`
  read endpoint + frontend fallback by `dataset_id`.
- **Status:** ⚪ uncommitted (from an earlier session).

## 5. Troubleshooting log

### 2026-08-07 — new dataset disappeared again
- Observation: a freshly created dataset vanished from the list.
- Hypothesis: #1 (cleanup cascade) still live on the server — the guard fix is
  committed locally but **not deployed**.
- Next step: deploy #1, verify, then create a clean dataset and confirm it
  survives a wrapper re-register + a restart.

**Findings (evening):**
- `grep -c remaining_links models.py` = **3** → **#1 guard IS now deployed.** ✅
- Orphan scan (`/tmp/find_orphans.py`): existing staged ids `[1-9, 28]`;
  **staged 29 (mal_pregnancy) GONE**, wrapper 283 GONE. Orphans = **source 279
  + mart 281** (`sv_29`, ~1,903 rows still in ClickHouse) pointing at staged 29.
- Interpretation: this is **pre-guard damage** — staged 29 was deleted before
  the guard went live. The guard prevents recurrence but cannot resurrect it.
  `mal_pregnancy` is invisible because staged dataset + wrapper are gone; only
  the raw serving tables remain (not shown in the METADATA-only list).
- **Open question:** was mal_pregnancy created *before* or *after* the guard
  deploy? Decides whether the guard is sufficient or a 2nd deletion path exists.
- **Next:** (a) delete the 2 orphans (279, 281) — safe now, staged 29 already
  gone so no further cascade; (b) recreate mal_pregnancy at **district level**
  with the guard live; (c) trigger a wrapper re-register (or restart) and
  confirm the staged dataset + wrapper **survive**. Log the result.
- If it survives → #1 confirmed sufficient. If it disappears again → hunt the
  second path (candidates: `create_staged_dataset` name-collision upsert;
  `register_metadata_dataset_as_superset_dataset` stale-record deletion).

**Findings (create test — REFRAME):**
- Created a new `mal_pregnancy_dataset` with the guard live; it "disappeared".
- `/tmp/post_create.py` shows: staged ids still `[1-9, 28]` (**no new staged**),
  newest SqlaTables are the **old** `sv_29` orphans 279/281 (**no new serving
  tables, no sv_30**), and **no new sync job** (newest is 3864 for staged 8).
- **New diagnosis:** this is NOT the cascade-delete (#1). The create **never
  persisted** — it **rolled back**. `create_staged_dataset` rolls back the whole
  ORM txn on any error; nothing lands (no staged, no serving, no job).
- **Prime suspect:** the leftover **orphan `sv_29` tables (279/281)** poison new
  creates — `register_serving_table_as_superset_dataset` matches existing
  SqlaTables by serving-table-ref / staged id and hits the orphans pointing at
  the dead staged 29 → error → rollback.
- **Next:** (a) capture the create error from `journalctl`; (b) delete orphans
  279/281; (c) retry create and confirm a new staged id + sync job appear.
- Note: #1 (cleanup guard) is still correct and worth keeping — it fixes the
  *cascade* class — but it is NOT the cause of *this* (create-rollback) failure.
  So there are (at least) TWO distinct failure classes:
  **(1) cascade-delete after create**, and **(2) create rolls back / never
  persists**, the latter likely triggered by leftover orphans.

**BREAKTHROUGH — the actual recurring root cause:**
- Deleting orphan 279 logged BOTH handlers firing back-to-back:
  1. `cleanup_linked_dhis2_staged_dataset: 1 other SqlaTable still references
     staged 29 — keeping it` → the **models.py guard worked**. ✅
  2. `DHIS2 listener: SqlaTable id=279 deleted; cleaning up DHIS2StagedDataset
     id=29` → a **SECOND, separate `after_delete` handler** in
     `superset/dhis2/listeners.py::_after_sqla_table_delete` that deletes the
     staged dataset with **NO guard** (it only skips MARTs). It **overrode** the
     models.py guard.
- So the "create rolls back" idea was a red herring. Real mechanism: the
  **unguarded listener** deletes the staged dataset whenever a SOURCE/wrapper
  SqlaTable is deleted — which happens on every wrapper **re-registration**.
  That's why datasets kept vanishing even with the models.py guard deployed.
- **Fix:** applied the identical "other tables still link?" guard to
  `_after_sqla_table_delete`. Both `after_delete` handlers now agree. Also
  repaired 2 stale tests in `test_cascading_delete.py`; **4/4 pass**.
- **Status:** models.py guard = deployed (`a60f614853`). **listeners.py guard =
  committed locally, DEPLOY NEXT** — this is the one that actually stops it.
- **Debt:** two overlapping `after_delete` handlers do the same cleanup;
  guarding one wasn't enough. Consolidate to a single guarded path later.
